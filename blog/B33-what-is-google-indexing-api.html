What is the Google Indexing API? How and When to Use It (2026)

By RankFrame Team  ·  May 4, 2026  ·  14 min read

The Google Indexing API is a programmatic interface that lets website owners notify Google directly when a page has been added, updated, or removed, prompting Googlebot to fetch the URL with priority instead of waiting for the next scheduled crawl. Officially, Google supports the API only for pages containing JobPosting or BroadcastEvent structured data. Unofficially, it has become one of the most widely used tools in modern SEO for accelerating discovery of any URL. This guide explains how it works, the official policy, the practical reality, how to set it up from scratch, and how to use it without writing code.

What is the Google Indexing API?

The Google Indexing API is an HTTP service launched by Google in 2018 that allows website owners to notify Google about new or changed URLs. When a request is sent to the API endpoint, Google adds the URL to a high-priority crawl queue and Googlebot typically fetches the page within minutes to a few hours. The intent of the API is to reduce the gap between content publication and search visibility for time-sensitive page types.

The Indexing API exposes two operations:

  • URL_UPDATED: tells Google that a URL has been added or its content has changed and should be recrawled.
  • URL_DELETED: tells Google that a URL has been permanently removed and should be dropped from the index.

The API endpoint is https://indexing.googleapis.com/v3/urlNotifications:publish. Each request is authenticated using OAuth 2.0 via a service account and contains a JSON body specifying the URL and the notification type. There is no batch endpoint in the standard sense, although Google does expose urlNotifications:getMetadata for inspecting the last submitted state of a URL.

The Indexing API is sometimes referred to as the "instant indexing API" because of how quickly Google responds to submissions. The phrase is informal. There is no Google product or feature literally called Instant Indexing. The term spread through SEO communities as a shorthand for the speed advantage the API offers compared to passive discovery methods.

How the Indexing API Differs from Sitemaps and URL Inspection

Google offers three primary mechanisms to communicate URL existence and changes to its crawler. Each works differently and serves a distinct purpose.

Sitemaps

An XML sitemap is a passive list of URLs hosted on your domain (typically at /sitemap.xml) that Googlebot reads on its own schedule. You submit the sitemap URL once in Google Search Console and Google revisits it periodically. Sitemaps are excellent for communicating site structure and lastmod timestamps but they do not trigger immediate crawling. A change reflected in the sitemap may not be picked up by Googlebot for hours or days, depending on how Google has scheduled crawling for your domain.

URL Inspection tool

The URL Inspection tool inside Google Search Console lets you manually request indexing for a single URL through a web interface. After clicking "Request indexing," Google adds the URL to a priority crawl queue. The tool is rate limited to roughly 10 to 12 requests per day per property and requires manual interaction. It is useful for one off pages but does not scale to dozens of URLs.

Indexing API

The Indexing API is programmatic. It accepts up to 200 requests per day per project by default, requires authentication via a service account, and can be triggered automatically whenever a page is published or updated. Submission is near instant from the publishing side and Googlebot typically crawls within hours. The API is the highest throughput option for prompting Google to fetch URLs.

Official Google Policy on Eligibility

Google's official documentation states that the Indexing API can be used only for pages containing one of two specific structured data types:

  • JobPosting: pages describing a job opening with structured data such as title, hiring organisation, location, and salary.
  • BroadcastEvent: pages describing a live video event embedded in a VideoObject schema, such as a livestream broadcast.

Google's reasoning for the restriction is that both content types are highly time sensitive. A job posting that closes in three days is useless to searchers if Google takes a week to index it. A livestream that starts at 8pm is useless if it appears in search results at 11pm. For these specific verticals, the API offers a measurable user experience benefit.

Google's stated position Google's official guidance is that submitting URLs that are not JobPosting or BroadcastEvent pages "may result in your access to the API being restricted." In practice, no widespread account suspensions have been reported for non-eligible submissions. The risk is real but historically rare.

The Unofficial Reality

Despite Google's stated restrictions, the SEO community has been using the Indexing API for general URLs (blog posts, product pages, landing pages) for years. The pattern is well documented across forums, case studies, and SEO tools. The observed behaviour is consistent:

  • Submissions for non-JobPosting and non-BroadcastEvent URLs are accepted by the API and return a 200 response.
  • Googlebot typically crawls the submitted URL within minutes to a few hours.
  • Whether the URL is then indexed depends on Google's normal indexing pipeline (quality, uniqueness, crawl signals).
  • Account suspensions or quota revocations for non-eligible submissions have been rare and not systematically reported.

SEO tools including Rank Math, Yoast, IndexMeNow, Indexing Insight, and many command line utilities expose Indexing API submission for any URL. Google has not taken action against these tools collectively, and they remain in active use. The ambiguity between official policy and observed reality is one of the longstanding discussions in technical SEO.

Our recommendation is straightforward. Treat the Indexing API as a crawl signal, not as a guaranteed indexing path. If your URL has JobPosting or BroadcastEvent schema, you are squarely within official Google guidelines. If your URL is a regular content page, the API can still help speed up discovery, but you should also rely on solid sitemap hygiene, internal linking, and content quality to ensure Google finds and indexes the page through normal channels.

How to Set Up the Indexing API

Setting up the Indexing API directly involves five distinct steps across Google Cloud Console and Google Search Console. Each step must be completed in order. If you skip ownership verification or miss the service account permission, the API will return authentication errors.

1

Create a Google Cloud project

Visit console.cloud.google.com, sign in, and create a new project. Give it a memorable name such as "Indexing API Production." Note the Project ID, which is needed later.

2

Enable the Indexing API

Inside the Cloud Console, open the API Library, search for "Web Search Indexing API" and click Enable. The service is free to enable. Without this step, requests to the API endpoint return a "service not enabled" error.

3

Create a service account

In the IAM and Admin section, create a new service account. Service accounts are non-human identities used by applications to authenticate with Google APIs. You do not need to assign it any IAM roles within the Cloud project. After creation, generate a JSON key for the account and download the file. The JSON key contains a private key that must be kept secret. Anyone with this file can submit URLs on behalf of your verified properties.

Treat the JSON key like a password Never commit the JSON key to a public Git repository. Store it as an environment variable or in a secure secrets manager. If the key is compromised, revoke it immediately in the Cloud Console.
4

Verify ownership in Google Search Console

If you have not already, verify your domain in Google Search Console using DNS, HTML file, or HTML tag verification. The Indexing API only accepts submissions for URLs on properties you own.

5

Add the service account as an Owner in Search Console

Inside Search Console, open the property, go to Settings, then Users and Permissions. Click Add User and paste the service account email address (it ends in .iam.gserviceaccount.com and is visible in your service account details). Set the permission level to Owner. Without Owner permission, the Indexing API rejects submissions for this property with a permission error.

How to Submit URLs (with Code Example)

Once setup is complete, you can submit URLs through any HTTP client that supports OAuth 2.0 service account authentication. Here is the structure of a URL_UPDATED request using a generic Node.js style example:

// Indexing API submission example const { google } = require('googleapis'); const key = require('./service-account-key.json'); const jwtClient = new google.auth.JWT( key.client_email, null, key.private_key, ['https://www.googleapis.com/auth/indexing'], null ); jwtClient.authorize(function(err, tokens) { if (err) { console.error(err); return; } const options = { url: 'https://indexing.googleapis.com/v3/urlNotifications:publish', method: 'POST', headers: { 'Content-Type': 'application/json' }, auth: { bearer: tokens.access_token }, json: { url: 'https://yourdomain.com/your-new-page', type: 'URL_UPDATED' } }; request(options, function(error, response, body) { console.log(body); }); });

The same request structure applies for URL_DELETED notifications. Replace the type field with URL_DELETED when a page has been permanently removed. A successful submission returns a JSON response with a notification metadata object including the timestamp of the submission. An unauthorized submission returns a 403 with a permission error message.

For a single ad hoc URL, the same request can be made using curl after manually generating an OAuth access token, but for production use a script that handles token refresh automatically is required. Most SEOs schedule submissions through a publishing hook (a CMS webhook fires on publish, the script submits the URL to the Indexing API) rather than running submissions manually.

Quotas and Limits

The default quota for the Indexing API is 200 publish requests per day per Cloud project. Each URL_UPDATED or URL_DELETED request counts as one against the quota. There is also a 600 request per minute rate limit on the metadata endpoint. The publish endpoint itself has no documented per-minute rate limit beyond the daily ceiling.

Operation Default daily quota Counts toward limit
URL_UPDATED 200 per day per project Yes (1 per URL)
URL_DELETED 200 per day per project (shared) Yes (1 per URL)
getMetadata 180 per minute Separate quota

You can request a higher publish quota through the Google Cloud Console by submitting a quota increase form. Approval is manual and not guaranteed. Sites that genuinely publish more than 200 new or substantially updated URLs per day (large news publishers, large job boards) typically get higher quotas approved without difficulty. Ordinary marketing sites and blogs rarely need a quota increase.

What Happens After Submission

A successful API call results in the following sequence:

  1. The URL is added to Google's high-priority crawl queue.
  2. Googlebot typically attempts to fetch the URL within minutes to a few hours. The exact delay depends on overall crawler load and your site's crawl health.
  3. If the fetch succeeds and the page returns a 200 status code, Google parses the content and runs it through the indexing pipeline.
  4. The indexing pipeline evaluates content quality, duplicate detection, canonicalisation, and crawl signals, and decides whether to add the URL to the index.
  5. If the page meets indexing criteria, it appears in search results within hours to a couple of days.

Critically, the Indexing API guarantees only step 1 and accelerates step 2. It does not bypass the indexing pipeline. Pages that are blocked by robots.txt, marked noindex, return non 200 status codes, are duplicates of canonical pages, or are considered low quality will not be indexed regardless of how many times they are submitted.

How to Verify the Result

After submitting a URL through the Indexing API, you can confirm what happened in two ways.

Use getMetadata

The Indexing API exposes a urlNotifications:getMetadata endpoint that returns the timestamp of the most recent URL_UPDATED or URL_DELETED notification for a given URL. This confirms only that Google received the notification, not that Googlebot has crawled or indexed the page.

Use the URL Inspection tool in Google Search Console

The most reliable way to confirm crawling and indexing is the URL Inspection tool. Open Google Search Console, navigate to URL Inspection, paste the URL, and check the report. Look for these signals:

  • Last crawl date: should reflect a recent fetch (within hours of API submission).
  • Indexing status: should show "URL is on Google" once indexed.
  • Crawl source: typically reads "Googlebot smartphone" for modern sites.
  • Canonical: confirms which URL Google considers canonical (sometimes Google chooses a different canonical than the one you submitted).

If the URL Inspection tool still shows an old crawl date 24 hours after API submission, something is wrong. Check robots.txt, the page status code, the noindex header, the canonical tag, and Search Console's indexing reports for clues.

For a complete indexing strategy, all three are used together. The sitemap communicates the full URL list. The Indexing API accelerates discovery for newly published or updated URLs. The URL Inspection tool is reserved for ad hoc cases where you need to debug a specific URL or force a recrawl outside of automation.
