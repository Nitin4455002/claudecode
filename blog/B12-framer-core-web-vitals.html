What Core Web Vitals Are (and Why They Matter for Framer Sites)

Core Web Vitals are a set of standardized, user-centric performance metrics that Google uses to measure real-world page experience. They are not abstract benchmarks -- they measure how a real user experiences the act of loading your page: how quickly content appears, how stable the layout is, and how quickly the page responds to interaction.

Google officially incorporated Core Web Vitals as a ranking signal as part of the Page Experience update. This does not mean a perfect performance score guarantees top rankings -- content relevance remains the dominant ranking factor. But among pages that are otherwise comparable in content quality and backlink profile, page experience (including Core Web Vitals) can be a tiebreaker. More practically, poor Core Web Vitals directly harm user experience, increase bounce rates, and reduce conversion rates -- all of which have downstream effects on your site's performance in search.

First Contentful Paint (FCP) measures the time from navigation start to the moment the browser renders the first piece of DOM content -- any text, image, canvas, or SVG. It is a measure of how quickly the user sees that something is happening. A fast FCP (under 1.8 seconds) reduces the perception of a slow or unresponsive page.

Largest Contentful Paint (LCP) measures the time from navigation start to when the largest visible element in the viewport has fully rendered. On most Framer landing pages, this is the hero image or the hero headline text. LCP is the most direct measure of perceived main content load time and is the metric that most Framer sites struggle with on mobile. Google's "good" threshold is under 2.5 seconds; "needs improvement" is 2.5 to 4.0 seconds; anything above 4.0 seconds is "poor."

Cumulative Layout Shift (CLS) measures the sum of all unexpected layout shift scores during the page's lifetime. A layout shift occurs when a visible element changes its position between frames -- for instance, when a font loads and causes text to reflow, or when an image loads without reserved space and pushes content down. CLS is scored as a unitless value; lower is better. The target is below 0.1.

Why Mobile Score Is the One That Counts

Google uses mobile-first indexing. This means Google primarily crawls and indexes the mobile version of your site. The Core Web Vitals data that Google collects through the Chrome User Experience Report (CrUX) is real-world data from mobile Chrome users. Your desktop Lighthouse score can be excellent while your mobile score is poor -- and it is the mobile score that affects your rankings.

For most visually rich Framer sites, the mobile Lighthouse performance score is 20 to 40 points lower than the desktop score. This is partly because Lighthouse simulates a mid-tier mobile device with a throttled CPU and slower network for mobile testing -- conditions that reflect the actual devices many of your users are on, particularly in markets outside North America and Western Europe.

Mobile-First Mindset When prioritizing performance improvements, test on mobile first and desktop second. A change that improves desktop LCP by 0.3 seconds is useful; a change that improves mobile LCP by 0.8 seconds is urgent. Focus your effort where Google's ranking signal is measured.

How Framer Handles Performance Natively

Framer's publishing infrastructure provides a solid performance foundation that most web builders do not match. Understanding what Framer does automatically helps you identify what is left for you to optimize.

Static Site Generation (SSG)

Framer generates static HTML files at build time rather than rendering pages dynamically on each request. This means when a user or Googlebot requests a page, the server sends a pre-built HTML file rather than executing server-side code. Static files are faster to deliver and eliminate server-side rendering bottlenecks.

Edge CDN Delivery

Framer delivers your static site through a global edge network. Your pages are cached at edge nodes geographically close to your users -- a visitor in Tokyo gets served from an edge node in the Asia-Pacific region rather than from a data center in the United States. Edge delivery reduces Time to First Byte (TTFB), which is a prerequisite for good FCP and LCP.

Rolldown Code Splitting

Framer uses Rolldown (a Rust-based JavaScript bundler) for code splitting -- the process of breaking your JavaScript into smaller chunks that can be loaded on demand rather than all at once. According to Framer's own benchmarks, Rolldown-based code splitting has delivered LCP improvements of up to 41% compared to previous bundling approaches. This means less JavaScript is blocking the main thread during the critical first paint window.

Automatic Image Optimization

When you upload images to Framer, they are automatically converted to WebP format (a modern image format that is 25-35% smaller than JPEG at equivalent visual quality) and served through Framer's CDN. Images are also resized and served at appropriate dimensions for the device viewing them. This automatic optimization handles a large portion of image-related performance overhead for images uploaded through Framer's native asset uploader.

Where Framer Falls Short Natively

Despite this foundation, Framer cannot optimize what you deliberately add to the design:

  • Heavy animations. Scroll-triggered animations, parallax effects, and complex entrance animations built with Framer Motion run JavaScript on the main thread and can delay FCP and LCP on mobile devices.
  • Third-party embeds. HubSpot forms, Typeform embeds, video players, Intercom widgets, and other third-party scripts load synchronously or near-synchronously and add significant JavaScript execution time that delays LCP and contributes to layout shifts.
  • Images larger than their display size. Framer's optimization works on images uploaded through the asset uploader, but oversized images that were already too large before upload can still be unnecessarily heavy.
  • Custom code components with unoptimized external dependencies. Any custom React component that imports a heavy library (charting libraries, 3D rendering, rich text editors) adds to the JavaScript bundle and delays FCP.
  • Fonts without explicit size reservations. Custom web fonts that are loaded asynchronously can cause text reflow (CLS) and delayed FCP if not configured correctly.

How to Measure Core Web Vitals for Your Framer Site

Measurement is the prerequisite for improvement. Without baseline data, you cannot know whether changes are helping or hurting, and you cannot prioritize which issues to fix first.

Google PageSpeed Insights

Google PageSpeed Insights (PSI) at pagespeed.web.dev is the free, authoritative tool for Core Web Vitals measurement. Enter your page URL and PSI returns two types of data: lab data (a Lighthouse audit run in controlled conditions) and field data (real-world data from Chrome users in the CrUX dataset, if your site has enough traffic).

Field data represents actual user experiences over the past 28 days. For ranking purposes, Google primarily uses CrUX field data rather than lab data. However, lab data (Lighthouse) gives you the specific file-level diagnostics needed to understand what is causing performance issues. Use lab data for diagnosis; use field data to confirm that improvements have propagated to real users.

Improving LCP on Framer Sites

LCP is the Core Web Vital that most directly reflects how quickly users see the main content of your page. For Framer sites, it is also the metric most likely to be in the "needs improvement" or "poor" range on mobile. LCP optimization on Framer sites follows a clear set of priorities.

Identify the LCP Element First

Before optimizing LCP, identify exactly which element Google is measuring as the LCP element on your page. Run your page through Google PageSpeed Insights and look for the "Largest Contentful Paint element" in the diagnostics section. This will tell you whether LCP is triggered by your hero image, a background image, or a large text block. The optimization approach differs significantly based on the element type.

Optimize the Hero Image

If the LCP element is a hero image (the most common case for Framer landing pages), the following optimizations apply:

  • Use WebP format. Framer's asset uploader converts images to WebP automatically. However, if you are using an external image URL in a custom code component, ensure that image is WebP or compressed AVIF.
  • Size images to their display dimensions. If your hero image displays at 1400px wide at maximum viewport width, your source image should be approximately 1400px wide (or 2800px for high-DPI retina displays). Uploading a 4000px wide raw export from Figma and relying on CSS to scale it down sends unnecessary bytes to every user.
  • Set explicit dimensions. In Framer's properties panel, ensure your hero image has explicit width and height values set. This allows the browser to allocate the correct space before the image loads, which also prevents CLS.
  • Use Framer's native image hosting. Images hosted on Framer's CDN are optimized and served from edge nodes. Images hosted on external services or raw GitHub URLs are not. Keep your images in Framer's asset library wherever possible.

Avoid Render-Blocking Resources

Render-blocking resources are scripts and stylesheets that must be downloaded and processed before the browser can render any content. Every millisecond spent on render-blocking resources directly delays FCP and LCP.

In Framer, the most common render-blocking additions are:

  • Synchronous third-party analytics scripts (older Google Analytics UA implementations, Hotjar, etc.)
  • Chat widget scripts (Intercom, Crisp, HubSpot chat) loaded in the <head>
  • Custom web font stylesheets without display=swap

For third-party scripts added through Framer's custom code injection, use the defer or async attribute to prevent them from blocking rendering. Place non-critical scripts at the end of the <body> rather than in the <head>.

Minimize Animation Initialization Before LCP

Framer's animation system initializes JavaScript before rendering begins. If your hero section contains heavy entrance animations (scale transforms, opacity fades tied to a complex intersection observer setup), the JavaScript initialization for those animations can push back the moment when the LCP element fully renders.

The simplest fix is to either remove entrance animations from the LCP element itself, or set a very short (under 100ms) delay before the hero section animation starts. This lets the browser render the LCP element first, then apply the animation overlay. The perceived visual experience is nearly identical; the LCP measurement improves significantly.

Animation vs. Performance Balance You do not need to remove all animations. Animations that run after the LCP element has already rendered do not affect the LCP score. The optimization target is specifically: do not let JavaScript execution for animations delay the initial render of the largest above-the-fold element.

Improving CLS on Framer Sites

Cumulative Layout Shift is often the most confusing Core Web Vital to understand and the most surprising to encounter on Framer sites. A site can look visually stable and still have poor CLS if elements are shifting positions during loading in ways that happen too fast for the designer to notice during preview.

Set Explicit Dimensions on All Images

The most common cause of CLS on Framer sites is images without explicit width and height attributes. When a browser loads an image without knowing its dimensions, it allocates zero space for the image initially. When the image data arrives, the browser reallocates space for it and shifts all surrounding content. This shift is measured as CLS.

In Framer's properties panel, set explicit width and height values for every image on your page -- particularly images in the first viewport (above the fold). For responsive images that scale with viewport width, setting at least the aspect ratio through Framer's frame properties accomplishes the same goal.

Framer's auto-layout components generally handle this correctly when images are placed inside frames with fixed dimensions. The problem typically arises with freeform canvas layouts, images inside rich text components, or CMS images where the dimensions vary by item.

Reserve Space for Third-Party Embeds

HubSpot forms, Typeform embeds, Calendly widgets, and video players (YouTube, Vimeo) all load content asynchronously. If the containing frame in Framer has auto-height or does not have fixed dimensions, the embed loads with zero height and then expands to its full height after the iframe content loads. This expansion is a significant layout shift.

The fix is to set a fixed minimum height on the containing frame in Framer that matches the typical rendered height of the embed. For a HubSpot contact form, set the container to at least 400px tall. For a YouTube video, the container should have the correct 16:9 aspect ratio reserved. This ensures that when the embed loads, it fills space that was already reserved rather than pushing content down.

Manage Font Loading to Prevent Text Reflow

Custom web fonts that load after the initial page render cause text reflow. The browser first renders text in a fallback system font (which has different character widths and line heights), then swaps to the custom font when it loads. This swap can cause paragraphs to change height, buttons to shift, and navigation items to move -- all contributing to CLS.

Framer's native Google Fonts integration includes display=swap by default, which allows text to be visible in the fallback font immediately and then swaps when the custom font is ready. However, the size differential between the fallback font and the custom font still causes reflow. To minimize this, choose fallback fonts that are dimensionally similar to your custom font, or use the CSS size-adjust property to bring fallback font metrics closer to the custom font metrics.

Avoid JavaScript-Triggered Layout Changes After Load

Any Framer component or custom code that modifies the DOM layout after the page has loaded contributes to CLS. This includes cookie consent banners that appear after a delay, pop-up modals that shift the scrollbar, notification bars that slide down from the top of the page, and chat widgets that expand from a floating button.

For cookie banners and notification bars, reserve the space they occupy from the initial render rather than inserting them into the layout after load. Use position: fixed overlays that do not affect the document flow rather than inserting banners into the page body.

Improving FCP on Framer Sites

First Contentful Paint is usually the easiest Core Web Vital to bring into "good" range on Framer sites because the platform's SSG and edge CDN already handle the heaviest lifting. When FCP is poor on a Framer site, it almost always traces back to render-blocking resources.

Defer Non-Critical Custom Code Components

Framer supports custom code components -- React components you write or import from npm packages. If a custom component loads a heavy JavaScript library synchronously, it blocks rendering until that library is downloaded and executed. The fix is to use dynamic imports in React (React.lazy with Suspense) to defer loading the component until after the initial render, or to restructure the component so its heaviest work happens after the critical rendering path completes.

If you are using a Framer plugin or community component that imports a large library (a 3D library, a charting library, a complex form framework), audit the component's bundle size. A single component that imports a 500KB library is a significant FCP risk on mobile.

Reduce Synchronous External Script Loads

Every synchronous script tag in your page's <head> blocks rendering. Review all custom code you have added to Framer's global code injection -- anything in the head section. Audit each script for whether it genuinely needs to run before the page renders. Most analytics scripts, chat widgets, and marketing pixels can be loaded asynchronously without any functional impact.

In Framer's Site Settings under Custom Code, move any scripts that do not need to block rendering to the "End of Body" section and add the async attribute. Analytics scripts are almost always safe to load asynchronously.

Third-Party Script Audit If your Framer site has added multiple marketing and analytics tools over time -- Google Analytics, Google Tag Manager, Meta Pixel, LinkedIn Insight Tag, Hotjar, Intercom, HubSpot tracking -- run a PageSpeed Insights audit and look at the "Reduce the impact of third-party code" opportunity. Each script adds to the main thread execution time. For sites with six or more third-party scripts, consider whether each tool is genuinely being used and generating value.

Core Web Vitals Score Targets for Different Framer Site Types

A single performance benchmark does not apply to every Framer site. An image-heavy portfolio showcasing high-resolution photography is inherently more LCP-challenged than a text-dominant SaaS pricing page. Setting realistic targets helps you evaluate whether your optimization efforts are achieving what is possible for your site type.

Site Type Mobile Target Desktop Target Biggest Challenge
SaaS landing page (minimal imagery) 80+ 95+ Third-party scripts
Portfolio (image-heavy) 65+ 85+ LCP from large images
Blog / content site 75+ 92+ Font loading, CLS
Agency website (animation-heavy) 55+ 80+ Animation JS, LCP delay
E-commerce / product catalog 70+ 88+ Multiple product images

These are realistic targets, not perfect targets. The goal is to be in the "Good" range for CWV metrics (LCP under 2.5s, CLS under 0.1, FCP under 1.8s) on mobile, not to achieve a theoretical perfect 100 score. A 100 Lighthouse score is practically impossible to maintain on a real Framer site with third-party integrations and dynamic content.

Portfolio and Photography Sites: LCP Is the Focus

For portfolio sites where the primary content is large, high-resolution images, LCP optimization dominates performance work. The key strategies are: export hero images at the correct display dimensions before uploading, ensure above-the-fold project thumbnails are not loading full-resolution exports, and consider a staggered loading approach where the first viewport image loads immediately and below-fold items load lazily.

Mobile scores of 65 to 70 are achievable for well-optimized image-heavy Framer portfolios. Trying to push beyond this while maintaining visual quality is a diminishing-returns exercise -- the remaining score gap typically requires trade-offs in image quality or design fidelity that are not worth making for a portfolio site.

SaaS Landing Pages: Third-Party Scripts Are the Focus

SaaS marketing sites on Framer typically have modest image requirements but accumulate marketing technology stacks over time. A common pattern: Google Analytics, a chat widget, a CRM tracking pixel, an A/B testing tool, and a heatmap tool all loaded on the same page. Each script adds 100 to 400 milliseconds to the main thread execution time on mobile.

For SaaS landing pages, the highest-impact optimization is almost always script management. Load tag manager asynchronously, defer chat widgets until after user interaction (most users do not need the chat widget before they read your headline), and consolidate analytics into a single tag manager container rather than loading multiple pixel scripts directly.

With good script discipline, SaaS landing pages on Framer can achieve mobile scores of 85 to 90 -- comfortably in the "Good" range for all Core Web Vitals.

Agency Websites: Animation vs. Performance Trade-Off

Agency websites built in Framer are often showcase pieces that push animation capabilities to the limit. Parallax hero sections, cursor-following effects, scroll-triggered reveal animations, and 3D canvas elements are all common. These features are what make Framer agency sites visually distinctive -- and they are also what drives mobile Lighthouse scores into the 40 to 60 range.

The practical approach is to accept lower mobile scores as a deliberate trade-off and focus on ensuring the Core Web Vitals raw values (LCP under 4s, CLS under 0.25) are at least in the "needs improvement" range rather than "poor." Search visibility for agency sites typically depends more on their content marketing, case studies, and backlinks than on marginal performance improvements. Completely removing animations to gain 15 Lighthouse points on mobile is not a rational trade-off for most creative agencies.

Reducing Animation Scope on Mobile Framer's responsive design controls allow you to disable or simplify animations specifically for mobile breakpoints. Consider using simpler fade-in animations on mobile while keeping the full parallax and scroll-trigger effects on desktop. This is a pragmatic middle ground that preserves the desktop showcase experience while improving mobile Core Web Vitals.
